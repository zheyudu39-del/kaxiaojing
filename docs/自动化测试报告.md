
## 三、后端接口审计

`api-audit.js` **从源码自动枚举**接口（不靠人工维护清单）：

1. 解析 `app.ts` 得到 `app.use('/api/xxx', routesFile)` 的挂载前缀
2. 逐个解析路由文件的 `router.<method>('<path>')`
3. 路径参数用样例值填充，得到完整 URL
4. 每个接口测「未登录」与「已登录（管理员）」两种身份

判定标准：`500` / 返回非 JSON / 请求失败 = **失败**；`401/403` = 鉴权正常；
`400/422` = 参数校验正常；`404` = 资源不存在（提示级）。

```

请求总数 : 508
✓ 正常   : 455
! 警告   : 0
i 提示   : 53
✗ 失败   : 0
```

### 关于「带 token 仍被拒」的 18 个接口

审计报告会列出 18 个「已登录仍返回 403」的接口（队伍消息、看板、队伍文件、问答编辑等）。

## 五、修复的缺陷清单

### 🔴 1. 队伍聊天可打挂整个服务进程（DoS）

**现象**：前端打开队伍聊天页 `/teams/:id/forum` 即导致后端进程直接退出。

**根因**：
- 前端 `TeamForum.tsx` 发的是对象：`socket.emit('join-team-chat', { teamId: N })`
- 后端 `socket/index.ts` 却把它当数字用：`socket.on('join-team-chat', (teamId) => ...)`
- 对象被当作 SQL 绑定参数 → sql.js 抛 `tried to bind a value of an unknown type`
- 该异常是**没有堆栈的字符串**，且 socket 处理器没有 try/catch
- 服务端**没有任何进程级异常兜底** → Node 直接退出

**影响**：任何人（无需登录）打开队伍聊天页，或直接发一个 socket 事件，就能让服务下线。

**修复**（四层防御）：
1. `parseTeamId()` 统一兼容「数字」与「{teamId}」两种形态并强制转正整数
2. `chatService` 入参强制类型收敛
3. `convertParams` 提前抛出**带堆栈的可捕获 Error**，替代 sql.js 的无堆栈字符串
4. `index.ts` 增加 `uncaughtException` / `unhandledRejection` 兜底

**验证**：`socket-teamchat-test.js` 覆盖 6 种载荷（含字符串、嵌套对象等非法值），
全部不再打挂服务。

---

### 🔴 2. 管理后台按类型筛选待审核内容必然 500

**现象**：`GET /api/admin/reviews?type=award` 返回 500。

**根因**：`reviewService.listReviewItems` 用 `subQueries.join(' UNION ALL ')` 拼接，
再 `ORDER BY created_at`。当按**单一类型**筛选时 UNION 只剩一个子查询，
`ORDER BY created_at` 就直接作用在带 JOIN 的查询上，而
`awards` / `users` / `competitions` 都有 `created_at` 列 →
`ambiguous column name: created_at`。

多类型时 UNION 输出列只有一个 `created_at`，反而不报错——所以一直没被发现。

**影响**：管理后台无法查看任何单一类型的待审核内容。

**修复**：`SELECT * FROM (${unionSql}) ORDER BY created_at DESC ...`，包一层派生表。

---

### 🔴 3. 本地开发所有写操作被 CSRF 拦截（403）

**现象**：浏览器里发帖、关注、点赞等**全部失败**，接口返回 403 `CSRF验证失败`。

**根因**：
- `vite.config.ts` 的 `/api` 代理设置了 `changeOrigin: true`，把 Host 改写成了 `localhost:5000`
- 后端 CSRF 中间件用「Origin 的 host === 请求的 Host」判定同源
- 浏览器发 `Origin: http://127.0.0.1:5173`，后端看到 `Host: localhost:5000` → 判为跨域
- 而 CSRF 对跨域请求**还要求 `X-Requested-With: XMLHttpRequest` 头**，
  前端从不设置该头 → 403

**修复**：`/api` 代理改为 `changeOrigin: false`，保持浏览器原始 Host，
后端即可正确识别为同源请求。

> 注意：只改了 `/api`，`/uploads` 与 `/socket.io` 保持 `changeOrigin: true`，避免影响 socket 的 CORS。

---

### 🟠 4. 管理后台审核列表字段名错位

前端读 `r.id` / `r.username` / `r.user_id`，接口实际返回
`content_id` / `submitter_name` / `submitter_id`。

**影响**：提交人列显示 `#undefined`；「通过 / 拒绝」请求
`/api/admin/reviews/posts/undefined/approve`，直接 400，**审核功能完全不可用**。

**修复**：`Admin.tsx` 改用正确字段（含详情弹窗）。

---

### 🟠 5. 审核类型参数名不一致，筛选静默失效

前端发 `?type=posts`，后端只读 `req.query.content_type` → 参数被忽略、
不筛选，列表混入所有类型，再拿错误的 type 去审核。

**修复**：后端兼容 `content_type` 与 `type` 两种参数名。

---

### 🟠 6. 审核类型单复数不一致

service 层用**单数**（`award` / `certificate` / `teacher_cert`），
前端下拉用**复数**（`awards` / `certificates` / `cert_study_plans`），
`cert_study_plans` 更是完全不同的词。

**修复**：后端入口统一做别名归一化，同时把前端下拉取值对齐为后端的规范值。

---

### 🟠 7. 可审核类型声明了实际不支持的三类

`VALID_CONTENT_TYPES` 含 `post` / `resource` / `recruitment`，
但 service 的 `TABLE_MAP` 没有它们，且这三类内容在创建时直接写入
`review_status='approved'`（**从不进入审核队列**）。
列在合法类型里，只会让前端给出永远 400 的选项。

**修复**：收敛为真正可审核的 4 类（`award` / `certificate` / `avatar` / `teacher_cert`），
前端下拉同步调整。

---

### 🟠 8. 组队匹配页「查看主页」全部指向 undefined

`/api/team-match` 返回的字段是 `id`，页面读的是 `m.user_id` →
每张卡片的「查看主页」都链到 `/users/undefined`，
进而请求 `/api/profile/undefined` 与 `/api/follows/NaN/counts` 双双 400。
**整页 9 个用户的跳转入口全部失效。**

**修复**：`TeamMatch.tsx` 中 4 处 `m.user_id` → `m.id`。

---

### 🟡 9. 赛事阶段更新缺参数校验

`PUT /api/competitions/:id/stages/:stageId` 未校验请求体，
而 `stage_name` / `start_month` / `end_month` 在表里是 `NOT NULL` →
缺字段时直接 500。同文件的 `POST` 有校验，`PUT` 漏了。

**修复**：补上同样的校验，返回 400。

## 六、未修复的观察项

### 1. 资料库 2 条资料链接到已删除的竞赛

`/resources` 中有 2 条资料的 `competition_id = 1`，
但竞赛 1 已不存在（详情接口 404，列表联表仍能取到名字，判断为软删除）。
点击后前端弹出错误提示。巡检中该页报的 2 项失败即为此。

**影响面小**（2 / 168 条），属于**数据问题而非代码缺陷**，
未做修改以免动到业务数据。

### 2. `/users/1` 的 409 是测试数据残留

巡检中 `/users/1` 点「关注」返回 409「已经关注了该用户」。
这是**正确的业务逻辑**——本次审计过程中该账号已关注过用户 1，
重复关注理应 409。

> 说明：`run-full-audit.sh` 每次都会重建干净的副本库，正常跑不会出现这条。
> 本次是手工复跑时复用了上一轮的库。

### 3. 后端 244 个既有类型错误

全部是 `@types/express` 5.x 与 express 4.x 不匹配的历史问题
（`req.query` 的 `ParsedQs` 类型），与本次改动无关。
项目以 `--transpile-only` 运行，不影响功能。

## 八、建议

1. **给 `join-team-chat` 这类 socket 事件补上参数校验的单测**——
   这类问题不会被接口审计覆盖，只能靠 socket 层测试。
2. **前端字段名与接口对齐应有约束**：本次 4 个缺陷（#4 #5 #6 #8）
   本质都是「前端按一套字段名写、后端按另一套实现」。
   建议为关键接口补 TypeScript 类型定义，让编译器兜住。
3. **CSRF 中间件的跨域分支目前无法通过任何前端满足**
   （要求 `X-Requested-With` 头，但前端从不设置）。
   若将来确实需要跨域部署，需要一并调整。
